## 0.7.1 修复与端到端通过

- 根因：原有 `button_event` 回调只转发 OK 的 PRESS/RELEASE，UP/DOWN 的原始按键事件被丢弃。先前仅直接调用语音模块的 host 测试无法覆盖这个入口遗漏。
- 抽出 `button_dispatch.h` 供真实回调使用，在输入模式允许 UP/DOWN 的原始按下/松开事件；新增 host 验证用同一个门禁将 UP PRESS/RELEASE 路由到实际语音模块，确认开始及排空录音。原有 Piko 页面的事件过滤行为保留。
- 加入选择电脑、开始/结束和块数的设备端诊断日志，不记录语音内容。原有回归及新增协议测试均通过，ESP-IDF 5.5.3 编译通过，生成 `build/piko-passport-0.7.1.zip`。
- 再次仅更新 `0x10000` 应用，esptool 哈希校验通过。串口确认 0.7.1 正常启动、ES8311 就绪、Wi-Fi 取得 `192.168.68.71`，Piko 重新认证成功。
- 设备日志确认选择电脑 `192.168.68.192`；三轮录音分别发送 16、17、25 个音频块，均正常结束且 `error=0`。
- 现有 Mac 客户端三轮均收到 `voice.start`、将首个音频块写入 BlackHole、收到 `voice.end`；客户端接收块数与设备一致。
- 通过文本编辑的 accessibility 状态观察到用户实际语音识别文字；未代替用户键入测试内容。用户明确反馈“出字了，回车正常”。本次没有改动微信输入法 F9/hold 配置。
- 更新期间客户端短暂报“设备静默超过 12s”，随后自动重新监听并发现设备，属刷写重启期间的断连；成功录音轮次没有新异常。
- 成功的第三轮录音之后 USB 串口从系统消失，监控因此结束；最后记录为 `end blocks=25 error=0`，没有崩溃标记。不能把计划的 120 秒监控时长当作实际完整观测时长。

结论：同一设备、当前 Mac 客户端、BlackHole 和微信输入法 F9/hold 环境下，已通过连接、按住录音、松开结束、真实出字及 Enter 验收。长期功耗、100 次模式切换、弱网及其他电脑/输入法版本仍未覆盖。
